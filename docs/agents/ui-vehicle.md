**统计**：`computeVehicleStats()` 用 `consumptionSegments()` **按 `vehicleId` 分别切段**算百公里能耗（`isFull === false` 的记录把加注量累加到下一满箱），旧数据缺 `isFull` 视为加满；加权平均用「总量 ÷ 总里程」，短里程段不会被赋予过高权重；油 / 电各自算均价与能耗；分段起点即 `lastFuelAnchor` / `lastChargeAnchor`；`tripInfo(records, current, type?)` 给出同车（可限定同类型）上一条的里程差、天数与里程倒挂判定。详细误差口径见下节。

**r32 估算兜底**：某台车某种能源**一次精确段都没凑出来**但有 ≥2 条记录时，用「第 2 条起累计加注量 ÷ 首末里程差」造一个 `estimated: true` 的段（排除第一条，它补的是首条里程之前消耗的量，没有对应起点）。估算段与精确段统一加权，仍按车分别算、不跨车混算。主卡按 `gasEstimated` / `electricEstimated` 分别加 `≈`；估算段的量已计入，不再挂 `pending`；`lastConsumption` 与加满锚点都跳过估算段，避免拿上一次满箱的旧值冒充新记录的结果。只有 0/1 条补能记录时没有里程差，仍显示「至少记两次加满」。

## 能耗算法与剩余油量误差口径（r32）

用户问「剩余油量还很多的话算法会不会有误差」，结论：

**加满法本身不因剩余油量产生误差**。两次记录都真加满时，起点与终点油箱液位相同、互相抵消，中间加进去的总量就等于这段里程真正烧掉的量；油箱里原本剩多少都不影响结果。所以「油还剩大半、只加一点」不是问题，前提是**如实标记为「没加满」**。

当前实现里真实会引入误差的地方（r31 已修前三条）：

1. **跨车混算（原 bug，影响最大）**：`computeVehicleStats()` 在「全部」态把三台车的记录按时间排成一条链，用 A 车的里程差去除 B 车的油量，数值完全不可用。现改为按 `vehicleId` 分组各自切段，再汇总。
2. **油电单价混加（原 bug）**：`avgPrice` 曾把 `L` 与 `kWh` 的 volume 直接相加，均价无意义。现拆成 `avgPriceGas`（元/L）与 `avgPriceElectric`（元/kWh），主卡按显示单位取。
3. **未结算分段不可见**：`isFull === false` 的油量累加到下一段，但如果一直没等到下一次加满，它会一直躺在 `pending` 里不参与统计；主卡看起来像「没更新」。现显式显示「本段已累计 X L，下次补满后计入」。
4. **误标「加满」**（数据层面，代码修不了）：跳枪 / 油枪提前停却勾了加满，会让起点液位低于终点，本次加满量偏大 → 算出油耗偏高。反之把真加满标成没加满，数据只是延后一段，不会算错。
5. **漏记一次加油**：那段里程被算进相邻分段而油量缺失 → 油耗偏低。
6. **混动车油电共用里程表**：同一次补能区间里既烧油又用电时，分母都是该区间的**总里程**，油耗与电耗会各自偏低。数据里没有「本段纯电里程」，无法精确拆分，当前按补能区间估算，别把混动车的单项数值当成实验室精度。
7. **短段权重**：改加权平均（总量 ÷ 总里程）前，逐段百公里值简单平均会让几十公里的短段与几百公里的长段等权。

**主卡锚点**取最近一段的起点（上一次加满 / 充满），按车切段后不会跨车串数据。示例数据里特意留了一笔 `isFull: false` 的 15 L 加油，用来演示第 3 条；小蓝的 6 笔「没充满」用来演示下面的估算路径。

### 不加满时怎么算（r32）

用户追问「那不加满会计算吗」，分三种情况：

| 情况 | r32 行为 |
| --- | --- |
| 单笔未加满，夹在两次加满之间 | 不做切点，量累加到下一个满箱一起算（**精确**），不会丢 |
| 一直没满箱、但 ≥2 条补能记录 | 该能源没有精确段 → 用累计量**估算**，主卡标 `≈` |
| 只有 0/1 条补能记录 | 没有里程差，估算也无从谈起，仍显示「至少记两次加满」 |

估算公式：`Σ(第 2..N 笔加注量) ÷ (末里程 − 首里程) × 100`，按车分别算再汇总。第一条的量必须排除（无对应起点里程）；这个口径与加满法里「起点那笔加满量不计入段内」一致。

**估算的误差**：起止油箱 / 电池液位差没被抵消，剩余量越多、记录越少，短期偏差越大；记录变多后液位差被摊薄，长期平均会收敛。所以估算值只作参考，**凑齐两次真加满就自动切回精确值**（`estimated` 段被精确段取代）。混动车 /「全部」态油电分别切段、各自标 `≈`，某台车精确另一台估算时一起加权，不做跨车混算。

**误标方向不对称**：把真加满标成「没加满」只是延后结算、不会算错；把没加满标成「加满」会把不完整的量当一整段，产生错误数字。**r33 起抽屉新增记录默认 `isFull: false`（`forms.tsx`），切「加油 / 充电」tab 也重置为未勾，且不再「记住上次」的勾选**，从录入侧消除风险最高的一侧；配合 r32 估算兜底，长期不加满也不会让主卡空着。改三态（加满 / 未加满 / 未标注）属于录入交互变更，需另行确认后再动。

## 与 APK 实测仍未对齐的部分

改之前先确认用户是否要补齐，别自作主张：

1. 「油耗趋势」独立柱状卡（我们只有每月花费）。
2. 「同步记账 / 付款账户」的真实写账本逻辑，涉及 bill entry 与账户体系，改动面较大。
3. 日期滚轮复用全局 `DatePicker`（datetime-local 5 列），APK 是年/月/日 3 列；标题文案 r30 已对齐为「日期」。
4. 补能类型用 5 类记录段控覆盖，APK 混动是「加油 / 充电」二选一段控；语义接近、版式不同。
5. 纯电主卡用 `kWh/100km` 单位区分，APK 额外有一条蓝色能耗线。
6. APK 纯电说明文案有个 bug：「充满了」下面仍写「两次加满之间才能算出油耗」，别照抄，写电耗。

## 已知约束 / 踩坑

- `components/vehicle/index.tsx` 的 `dialogTitle` 是无障碍标签，曾硬编码英文；**应用无英文名**，已改「车辆」/「车辆记录」。
- **日期后面的 `L`**：`DatePicker` / `WheelDatePicker` 默认 `displayFormatter` 是 dayjs 的 `"L"`，项目没加载 `localizedFormat` 插件时 `L` 会作为字面量显示。车辆记录抽屉必须传 `displayFormatter={() => ""}` 并自己渲染日期文本；不要为此改全局日期组件，其它调用点依赖默认行为。
- **备注「选填」只出现一次**：由右对齐 `input` 的 placeholder 提供。验证脚本读 `input.placeholder`，`placeholder` 不进 `innerText`。
- 「全部」态打开记一笔时默认车来自上一次同类型记录（可能不是燃油车），断言「燃油车不出现充电」前必须先显式点「小白」并确认顶部类型是「加油」。
- 车辆卡横向滚动区是 `flex min-h-0 flex-1 flex-col overflow-y-auto` 父容器的 flex item，必须加 `flex-shrink-0`，否则长页面会把它压成 0 高（WebKit 实测）。
- 三栏指标 label 用 `truncate`：长文案会被截断，单位放在 value 后面。
- 语言键集中在 zh/en 的 `vehicle-*` 段；新增键用独立 `.py` 脚本追加并 `json.load` 校验，脚本必须 `write_bytes()` 保持 LF（`write_text` 在 Windows 会转成 CRLF 造成整文件 diff）。页面回归必须查 `document.body.innerText` 里有没有 `vehicle-[a-z-]+` 泄漏。
- `createConfirmProvider` 只透传 `edit / onCancel / onConfirm`，所以删除回调要塞进 `edit`（`VehicleFormEdit` / `VehicleRecordForm` 的 `edit.onDelete`），不能在 props 上加 `onDelete`。`createDeleteConfirm()` 的 Provider 必须挂在**抽屉组件内部**，否则确认弹窗不会出现；确认后调 `onCancel()` 关抽屉，`showXxx()` 会 reject，页面已有 `.catch(() => undefined)`。
- 「距上次」的锚点必须限定同类型：不传 `type` 时 `tripInfo()` 找的是上一条任意记录，会把「距上次加油」算到中间那笔维修上。
- 统计值以 `[data-vehicle-page] span.text-brand` 的大字为准做验证断言；「全部」态是三台车分段汇总，数值合理区间约 5~10 L/100km、10~20 kWh/100km，出现几十以上基本就是又跨车混算了。
- **5173 是 `dist` 预览不是 dev server**：改完源码必须重新 `vite build --no-emptyOutDir` 才会被验证脚本看到；曾因为漏重建，连续两轮双引擎都跑在旧 bundle 上，误判「静默 catch 没生效」。
- **取消 Promise**：从抽屉导航到路由页会触发「manually cancelled」的 reject，`confirm/state.ts` 与 `confirm/index.tsx` 已在源头静默 catch，`ProfileAvatar` 的 `showProfile()` 调用点也补了 `.catch(() => {})`；否则浏览器报 `Unhandled Promise Rejection`。
